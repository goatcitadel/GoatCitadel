# Cockpit Inbox change-signal implementation and audit

Date: 2026-09-30. Scope: current isolated cockpit source. The bounded publisher below is implemented and has focused source tests; matching named realtime and built-browser proof remains a separate checkpoint.

## Conclusion

The Phase 3 `inbox.changed` publisher now derives invalidation in the existing `RealtimeEventService` from an allowlisted, already-persisted owner signal, then uses the existing idempotent retained-event append and safe live-emission path. It adds no owner service, domain repository access, storage migration, architecture allowance, or GatewayService changes.

This closes the dedicated signal gap for the audited existing producers. It cannot supply missing domain transitions, make a bounded Inbox count complete, or make every projected family eligible for a toast. Existing 30-second Inbox refresh remains necessary for owners without signals and time-dependent projections.

## Existing publication boundary

- [`RealtimeEventService.publishRealtime`](../apps/gateway/src/services/realtime-event-service.ts) validates protected metadata, strips the reserved delivery envelope, redacts public payload, awaits `realtimeEvents.append` or `appendIdempotent`, then emits only newly inserted events. Throwing listeners are isolated after persistence.
- [`RealtimeEventRepository.appendIdempotent`](../packages/storage/src/realtime-event-repo.ts) accepts a deterministic delivery ID and original occurrence time, verifies repeated payload identity, and does not allocate another event on the same retained delivery. SQLite and PostgreSQL use this repository boundary.
- [`GatewayService.publishRealtime`](../apps/gateway/src/services/gateway-service.ts) delegates to that service, then separately handles mobile push and canonical notification routing. The invalidation stays inside the existing realtime owner and does not re-enter this wrapper or external notification routing.
- [`events.ts`](../apps/gateway/src/routes/events.ts) subscribes before replay, buffers live events while replay is read, and suppresses sequences already delivered. Replay/list methods only read persisted events; they must not derive or publish invalidations.
- Persisted realtime is a retained operator signal, not transaction authority. The publisher cannot establish that an arbitrary caller has committed its domain transaction. Admission therefore needs an exact audited producer allowlist, not a keyword match over all `system`, `failed`, `proposal`, or `changed` events.

## Implemented first slice

1. Add a small pure `inbox-change-signal.ts` helper in the existing services directory. Accept a persisted `RealtimeEvent`, reject `durable_history`, `derived_projection`, malformed identities, `inbox.changed`, and non-allowlisted producer pairs. Start with committed approval create/resolve, exact change-plan events, task deliverable/create/update/delete, exact Chat thread updates, and audited durable terminal/recovery transitions. Memory candidate transitions and improvement post-transaction review events can be added when their exact caller evidence is covered by tests. Avoid broad source/topic regexes.
2. Return only an invalidation envelope: `eventType: "inbox.changed"`, a dedicated source such as `operator_inbox`, `eventClass: "operational_signal"`, `eventAuthority: "retained_stream"`, source-event ID, bounded family identifier, and explicit scope (`workspace` with the source's exact workspace link, or `all_workspaces` when no workspace is provided). Do not copy title, message, status claims, tokens, raw payload, or counts. If two structured workspace bindings disagree, reject the signal rather than choose one.
3. Use deterministic delivery ID `inbox.changed:<sourceEventId>` and the source timestamp. Refactor the existing persistence-and-emission block into one private reusable method for both original and derivative; retain the same repository operations and receivers. This is genuine reuse of retained publication, with no additional dependency access and no recursive call to public `publishRealtime`.
4. Derive only while handling a publish, never while reading replay. Emit the derivative only if its idempotent append reports `inserted`. A repeated original delivery may attempt the same derivative append to repair an earlier derivative persistence failure; it must not emit twice. A derivative failure must produce a bounded diagnostic and must not turn the already-committed original event/domain mutation into a retryable failure. Existing owner signals and refresh remain the recovery path.
5. Give `inbox.changed` an explicit early invalidation-only branch in shared notification derivation. Cockpit invalidation should target the linked workspace query when provided, or all Inbox queries for explicitly unscoped invalidations. Replayed invalidations may refresh; they never create attention, sound, desktop notices, or another server publication. Existing original attention signals continue to require a fresh exact owner item before toasting.
6. Leave missing source publishers, archive-on-view state, and additional attention resolvers as separate bounded work. Do not claim this first slice signals every possible Inbox change.

The first slice implements items 1–6 above in [`inbox-change-signal.ts`](../apps/gateway/src/services/inbox-change-signal.ts), the existing realtime owner, shared notification derivation and cockpit invalidation. Memory, document, capability and improvement producer additions remain excluded. The admitted `chat_thread_updated` callers publish terminal/waiting post-commit checkpoints, not streaming token deltas.

The architecture checker reports nine dependency accesses for `RealtimeEventService` and zero for the pure mapping helper. The parent-run `2026-09-30T13-58-27-787Z-architecture-metrics-29414449` checkpoint retains the same 16 inherited failures; the new publisher does not add one. No baseline, cap or owner allowance changed.

## Focused proof seams

- Pure mapping tests: every admitted exact source/type pair; foreign/non-admitted pair; history/projection rejection; explicit workspace; absent scope without a default; contradictory scope; secret-bearing original payload not copied; derived event never maps again.
- Existing realtime service tests plus real storage coverage: source append occurs before derivative append/live emission; original append failure emits neither; source returned unchanged; original and derivative each emitted once; idempotent retry does not duplicate either; failed derivative does not fail the original; list/replay cannot append; throwing subscribers remain isolated. Existing fake-storage tests return deliberately incomplete events in some cases, so the helper should fail closed on those fixtures rather than weaken their original assertions.
- Existing approval outbox tests: no `inbox.changed` before the creation/resolution transaction commits; rollback creates neither signal; redacted action-token handling preserved.
- Existing task/durable/plan tests: one representative canonical transition for each admitted family, with explicit post-commit observation. Existing SQLite/PostgreSQL retained repository tests establish the persistence interface; add parity cases only if repository behavior changes.
- Cockpit/shared tests: scoped and global query invalidation; `inbox.changed` never yields notification; replay remains silent; counts still come from projection. The current browser approval journey can assert the exact derivative references its observed live `approval_created` and triggers no second toast.
- Executed focused tests: `inbox-change-signal`, `realtime-inbox-publication`, and existing `realtime-event-service` passed 69/69; cockpit realtime/notification/item resolution passed 31/31; shared realtime derivation passed 12/12. The real SQLite publication fixture proves idempotence, persistence ordering, original/derivative failure separation, replay silence, isolated listeners and token exclusion. Its real TaskLifecycleService deliverable test observes the canonical record before the live invalidation. Scoped ESLint and `git diff --check` passed.
- Required follow-up lanes: `verify:realtime:truth`, `verify:gateway:async-boundary`, and matching built-browser proof. These focused tests do not establish complete approval/plan/durable producer coverage, PostgreSQL runtime proof, or all-family delivery. Source tests use disposable storage and did not mutate the user's runtime.

## Attention and count truth

[`resolveInboxNotificationItem`](../apps/mission-control-next/src/cockpit/data/inbox-notification.ts) currently accepts only exact approval-waiting, operator-blocked question/plan, failed run/dead letter, completed watched child, and task-deliverable families. It checks projection scope/authority, expiry, linked session/turn/run, and returns an item only when exactly one matches. A failed run with both a failure row and unresolved dead letter, or a task with multiple recent deliverables, is intentionally ambiguous and receives no guessed toast.

Remaining unsupported attention is real: `runtime_degraded`, generic owner-authored `ui_notification`, and replay-gap attention do not have a cockpit Inbox item resolver. Change-plan waiting notifications often lack enough linked run/session/turn identity for that resolver. Memory/document/capability/improvement proposals refresh but are not currently a toast attention kind. A new invalidation event must not be advertised as fixing those gaps.

[`buildInboxProjection`](../apps/gateway/src/services/inbox-projection-model.ts) computes each `known` count from returned owner-backed rows; `complete` reflects source coverage. Runtime health and Updates are explicitly partial; limits, unreadable owners, missing or contradictory scope reduce completeness. [`useOperatorInbox`](../apps/mission-control-next/src/cockpit/data/use-operator-inbox.ts), sidebar, phone navigation, and Inbox use the same scoped query. [`inbox-presentation.ts`](../apps/mission-control-next/src/cockpit/areas/inbox/inbox-presentation.ts) withholds crossed scope and renders unknown/lower-bound counts. Events do not increment these counts. Toasts show a matched current item, not an independently maintained count.

The design also requests Updates archive automatically after viewing. Current projection has no read/archive state and the view exposes no corresponding owner action; this remains an explicit gap, separate from invalidation. The installed clean-profile first-run gate remains deferred by the user, and active delegated-child admission still cannot be fabricated for proof.
