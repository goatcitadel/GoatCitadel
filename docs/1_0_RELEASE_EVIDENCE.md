# GoatCitadel 1.0 Release Evidence

Last updated: 2026-06-01

This document maps the public `1.0` claims to the repo-visible code paths, tests, and named verification lanes that back them.

For this document:

- `proof` means a named verification lane with a bespoke scenario body under [scripts/verification/lib/scenarios.mjs](../scripts/verification/lib/scenarios.mjs) or a targeted contract/behavior harness; lanes that are not live end-to-end proof must say so explicitly
- `evidence` means the supporting repo-visible code paths, unit/integration tests, and manifests that anchor those claims

Current shell posture for this map:

- `apps/mission-control-next` is the canonical `1.0` shell.
- `apps/mission-control` was retired in Track D Phase 3 (source archived from disk). All operator surfaces are owned by `apps/mission-control-next` and the shared packages it consumes.
- `release-certificate.json` is the commit-bound proof record for signed public Windows installer releases. Source/dev/onboarding 1.0 readiness is backed by the named verification lanes below; public-trust EXE distribution additionally requires a green release certificate with an empty `acceptedFailures` array. The `v1.0.0` GitHub release may include unsigned Windows convenience installers, but those assets are not Authenticode-signed and do not carry release-certificate public-trust status.
- Required lane workflows run directly on relevant PR/main changes. The umbrella `Verification 1.0 Release Proof` workflow can be dispatched or tag-triggered on a release-candidate SHA to refresh the umbrella-covered required lanes; direct-only lanes such as `docs:check` and `security:trivy` still require their own exact-SHA workflow evidence.
- Signed release publication writes the release certificate from exact-SHA lane evidence. Umbrella proof can cover only missing or unavailable direct runs for umbrella-covered lanes, so tag-triggered installer builds cannot race ahead of direct-only proof or hide direct lane failures. Unsigned convenience-installer publication must cite the same exact-SHA proof lanes without claiming a signed release certificate.
- The final certificate is written only after signed installer hashes are known, so it is not embedded back into the installer. The release job instead publishes `*-verified.zip` Windows distributions containing the signed installer plus a fixed `release-evidence/` sidecar directory. Inno copies that directory to `app/release-evidence` when the installer is launched from the verified distribution. A standalone installer remains supported, but the running shell must report its release proof as unverified because the certificate-bound files are absent.
- The current operator IA is `Work / Projects / Library / Ops / Settings`, where Work is Chat; `Work / Observe / Tune` is legacy release taxonomy, not the current shell navigation.

- Desktop external opening and WebView navigation are constrained by URL validation before handing a target to the OS or WebView2 in [apps/mission-control-windows/Services/NavigationPolicy.cs](../apps/mission-control-windows/Services/NavigationPolicy.cs) and [apps/mission-control-windows/Services/OpenTargetService.cs](../apps/mission-control-windows/Services/OpenTargetService.cs).
- Desktop compile and unit-test proof is wired through `pnpm verify:desktop`, which now requires the .NET 10 SDK on Windows, runs the Windows host unit tests, keeps Tauri `cargo check` / `cargo test` while rollback code remains, and validates launcher status JSON plus desktop SSE credential shape in [scripts/verify-desktop.mjs](../scripts/verify-desktop.mjs).
- Windows bundle trust is anchored by checksum verification for the embedded Node archive in [scripts/packaging/build-bundle.mjs](../scripts/packaging/build-bundle.mjs).
- Signed public Windows releases build the sparse external-location package identity with `pnpm package:windows-msix`, embed it as `app/identity/GoatCitadel-Mission-Control-Windows-Identity.msix`, register it with `Add-AppxPackage -ExternalLocation` during Inno install, and record the `mission-control-windows-identity-package` manifest component only when the identity MSIX is signed. The package publisher value comes from the public release variable `WINDOWS_MSIX_PUBLISHER` / local `GOATCITADEL_WINDOWS_MSIX_PUBLISHER` and must match both the signing certificate subject and the WinUI executable's embedded package identity. Unsigned local MSIX builds are allowed only for manifest/tooling proof and are skipped by bundle generation.
- Tagged public Windows releases must build the Windows App SDK host, sign and verify both the desktop executable and final installer, validate x64/arm64 artifact completeness, and run the signed mode of the shared [Windows installer lifecycle smoke](../scripts/packaging/smoke-windows-installer.ps1) before upload in [.github/workflows/release-installers.yml](../.github/workflows/release-installers.yml). Signed mode requires coherent installer, installed desktop, and installed-identity signatures; exact protocol/package identity binding; byte equality with the detached clean target manifest; and independent installed-payload hash validation. The isolated smoke refuses pre-existing GoatCitadel registrations and clears ambient launcher/endpoint overrides before host startup. The same workflow now also carries experimental Linux x64 tarball publication with checksum/archive smoke and an experimental macOS arm64 DMG path that is fail-closed on Developer ID signing, notarization, stapling, checksum, and DMG smoke. The signed public release gate remains closed until the mandatory external GitHub controls below are configured.
- Manual `workflow_dispatch` runs with `allow_unsigned=true` build x64/arm64 unsigned installers, run the unsigned mode of that same desktop launch/runtime/install/uninstall smoke, run Linux archive smoke, run ad-hoc non-notarized macOS DMG smoke, and upload workflow artifacts named `*-unsigned-package-smoke-assets` or `*-experimental-package-smoke-assets`. Unsigned mode permits the package identity to be omitted or unsigned while preserving every non-trust lifecycle assertion. Manual runs cannot enter PFX, Apple, OIDC-signing, or GitHub Release publication jobs. Those artifacts may be attached to `v1.0.0` as unsigned or experimental convenience artifacts, but they must be labeled as unsigned/experimental and must not be described as public-trust signed distribution.
