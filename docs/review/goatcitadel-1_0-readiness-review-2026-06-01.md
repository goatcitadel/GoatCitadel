## Verdict

**Conditional Go — but not from *this* tree as it stands today.**

The engineering substrate is genuinely 1.0-grade: disciplined tests, enforced coverage,
a large CI/verification fabric, a real security audit with fixed-and-regression-tested
findings, and the headline Critical bug from the last full review **confirmed fixed in
HEAD**. The product-gap "1.0 is premature" reviews are stale — their P0 surfaces (Trust &
Policy, Universal Run Detail, semantic memory, Ops quality dashboard) shipped.

But three current, concrete conditions block tagging a release *right now*:

1. **The working tree is mid-development** — 79 uncommitted changes, including new
   security-sensitive subsystems. You cannot certify 1.0 on an uncommitted, CI-unproven tree.
2. **The architecture-metrics ratchet is already over baseline** in the working tree and will
   re-red a required CI lane the moment this work commits.
3. **The 2026-05-28 full code review's High backlog is only partially landed** on this `main`,
   and at least one "ship-disabled defense" finding is still live.

None of these are deep/structural. They are "finish, commit, prove green, reconcile claims"
items. Net: **Go, conditional on the gating checklist below** — realistically days, not weeks.

## The three gating conditions (must clear before tagging)

### G1 — The tree is uncommitted and CI-unproven (79 changes)

`git status` shows **58 modified + 21 untracked**, including a coherent new feature landing
that is *not yet committed*:

- `apps/gateway/src/code-mode-hostile-sandbox-proof.ts` + `code-mode-sandbox/hostile-canary-runner.ts(.test.ts)` — adversarial canary proof harness
- `code-mode-sandbox/{windows-appcontainer,darwin-seatbelt,linux-firejail}-adapter.ts` — sandbox hardening
- `apps/gateway/src/services/mcp-oauth-token-service.ts` — remote-MCP OAuth (authz-code + refresh, tokens in OS secret store)
- `apps/gateway/src/services/autonomous-activation-grant-service.ts` + `packages/contracts/src/autonomy.ts` — operator-issued expiring autonomy grants

A focused read-only assessment found this work **complete, coherent, fully wired (contracts →
service → routes → runtime → docs → a dedicated `verify:code-mode:hostile-sandbox` lane), and
truth-gated** — which is reassuring. But "well-engineered and uncommitted" is still not "1.0".
The release certificate is generated by CI from a committed, tagged state with an *empty*
`acceptedFailures` set; you cannot produce that from a dirty tree.

**Action:** land this work as reviewed, committed PRs; then cut the candidate from a clean tree.
(Operational note: this repo's worktree is shared with other agent sessions — re-check `HEAD`
and `git status` immediately before any commit/tag so a concurrent session doesn't reset it.)

### G2 — Architecture-metrics ratchet is already red in the working tree

The committed baseline (`scripts/verification/baselines/architecture-metrics.json`,
regenerated today) pins `gateway-service.ts` at **9047** lines. The working-tree file is now
**9133** (+86). `verify:architecture:metrics` is **PR-gating** via `verification-truth-lanes.yml`
(`pull_request` paths on `apps/**`, `packages/**`). So the moment the in-flight work commits,
**any PR touching app/package source inherits a red required job** — the exact CI-001 / C2
failure mode the 2026-05-28 review called out, recurring.

`chat-agent-orchestrator.ts` (15,203) and `prompt-pack-service.ts` (9,516) remain the tracked
monolith debt; `capability-system-service.ts` grew to 3,816 absorbing the new grant logic.

**Action:** either decompose `gateway-service.ts` back under baseline, or consciously bump the
baseline *with reviewer sign-off* — and stop letting the ratchet drift red (it has done so
repeatedly; this is accepted-debt creep, not a one-off).

### G3 — The 2026-05-28 review's High backlog is only partially landed

That review (16 parallel adversarial reviewers, ~250 findings, 2 Critical + ~36 High) is the
most authoritative artifact in the repo. Its claimed fix-PRs **#30–#38 are not present in this
`main`'s history** — recent commits are *feature* work (native memory queue, Activepieces
evidence, portable skill bundles, security-eval lane), not the B1 bug batch. Spot-checks:

- ✅ C1 (Anthropic tool-calls) — **fixed** in HEAD.
- ❌ AGENTORCH-002 — `config/tool-policy.json:63` still ships `loopDetection.enabled: false`
  (the no-progress/loop guard never runs). "Trust theater" finding still live.

I did not re-verify all ~36 Highs (that's a full re-review, out of scope for a readiness
pass), but the sample shows the backlog is **not** closed on this branch. Several of those
Highs are real production risks, not cosmetics:

- `STORAGE-002` mesh-lease split-brain (non-atomic acquire/renew) — only safe single-process
- `COREPKG-017` secret-redaction regex misses in-value/contains-key secrets
- `INTEG-001/002` channel bot-loop guard is dead code; no sender allowlist on Slack/WhatsApp/LINE
- `INFRA-001/002` MCP stdio children → Windows zombies / EPIPE can crash the gateway
- `IMPROVE-001` decision-replay auto-tune writes runtime settings with no approval gate

**Action:** triage the 2026-05-28 Highs against current HEAD, land the genuine ones, and
record the rest as explicitly-accepted, ticketed post-1.0 debt. Don't ship with "documented
defense that is dead code" — that's the single worst look for a trust-branded product.

## Truth-first watch item (sign-off, not a hard blocker)

The Windows sandbox adapter relabels five checks from `*_not_enforced` (was in `checksFailed`)
to `*_intended` (now in `checksPassed`), which flips `metadata.available` **false → true** on
Windows because `available = checksFailed.length === 0` (`code-mode-sandbox/types.ts:74`). The
launcher genuinely improved (real AppContainer + job limits + stdio JSON-RPC), but
`available: true` now reflects *intent*, not *verified enforcement*.

This is **contained**: the user-facing hostile-code claim is a separate field
(`hostileSandboxClaim.publicClaimAllowed`) that stays `false` until all three platforms pass
every canary, so nothing over-advertises isolation. But "intended ≠ enforced" gating a
capability's `available` flag is precisely the wording a truth-first brand polices.
**Action:** explicit reviewer sign-off that `*_intended` is an acceptable basis for
`available: true` on Windows, or rename to make the intent/enforcement distinction legible.

## Fast-follow (do NOT gate 1.0)

- **Install-path signing (DESKTOP-001):** `iwr … | iex` + unpinned `git clone` bypasses the
  release-signing chain. High-ish for a security product; worth a pinned/checksummed installer
  soon, but the signed Windows proof-package path already exists alongside it.
- **CI false-confidence (CI-002/004/005):** ESLint runs in *no* CI workflow; provider "truth"
  lanes count auth-fail/404 as `not_configured` (green with zero working providers); the only
  always-on PR lane runs `AUTH_MODE=none`. These make green lanes mean less than they look.
- **`eslint-plugin-react-hooks` installed but not wired** into `eslint.config.mjs` →
  `exhaustive-deps`/`rules-of-hooks` unenforced (root cause of the MCNEXT/MCSHARED async-guard
  cluster). Note: enabling it repo-wide trips the known mission-control eslint-scope caveat.
- **Minor cleanups:** dead ternary `mcp-oauth-token-service.ts:97`; autonomy grant counters can
  over-count on aborted Code Mode runs (conservative direction — over-restricts, not a hole).
- **Provider smoke / package owner metadata** before public package publication
  (per `production-readiness-edge-cases-2026-05-23.md`).
- Gateway monolith decomposition continues as tracked debt (orchestrator 15k, prompt-pack 9.5k).

GoatCitadel is a credible 1.0 — the architecture, test discipline, security posture, and the
governance surfaces the old reviews said were missing are all real and present. The gap between
