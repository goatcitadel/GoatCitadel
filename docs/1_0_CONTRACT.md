# GoatCitadel 1.0 Contract

Last updated: 2026-10-11

This document defines the product promise, visible scope, trust posture, upgrade guarantees, and release gates required before GoatCitadel may describe itself as `1.0`.

**2026-10-11 profile-free Chat restoration:** New turns continue to use live callable capabilities with Gateway policy checks at exposure and invocation. No new all-purpose capability profile or catalog is frozen. Independent default-off switches restore selected skill instructions, bounded tool exposure, configured provider fallback, explicit context, supervised/automatic delegation, scheduled Chat, heartbeat work and selected static/requester MCP and mesh bindings through existing durable owners. Immutable admission references retain selected content and routing evidence; they never replace current policy, grants, scope or connection checks. Requester MCP requires a Gateway-owned actor-bound resolver. Remote placement has a default-off admission variant through existing C5 owners; full live and two-machine acceptance remain incomplete; Work Passport, model council and workspace snapshots are restored profile-free and on by default (`chatWorkPassportV1Enabled`, `chatModelCouncilV1Enabled`, `chatWorkspaceSnapshotV1Enabled`) through the turn's immutable feature references. Historical frozen records retain guarded replay. See [Feature quality execution](testing/FEATURE_QUALITY_EXECUTION.md) for restrictions, flags and evidence; this work does not certify a release or comparative parity.

For `1.0` governance language:

- `proof` means a named verification lane with a bespoke scenario body or targeted contract/behavior harness; lanes that are not live end-to-end proof must say so explicitly
- `evidence` means the repo-visible code, tests, manifests, and supporting docs that anchor those claims

## Product Promise

GoatCitadel `1.0` is a local-first AI workbench for technical users who need to plan, supervise, and execute AI-assisted work across conversation, structured workflows, and code.

OpenCode is an optional external coding agent through the bundled `opencode` skill and the existing approved `shell.exec` path. The operator supplies a locally installed, independently authenticated CLI. Foreground commands retain the 20-second default and may request a bounded `timeoutMs` of 1–900 seconds; cancellation still terminates the owned process tree. Direct `opencode run --format json` output is redacted and projected into bounded Chat result cards with agent steps, reported files, and expandable diff previews. The projection survives raw-output artifact compaction. Progress within OpenCode is captured at process completion, not streamed as individual Gateway tool calls. OpenCode's internal permissions and provider configuration remain its own; approving the parent process does not establish per-action Gateway enforcement or hostile-code sandboxing. See [OpenCode integration](./OPENCODE_INTEGRATION.md).

The `1.0` promise is:

- human-in-the-loop approvals for risky actions
- truthful runtime state and replayable operator evidence
- resumable execution for the shipped durable flow set
- multi-provider operation with explicit runtime diagnostics and support truth
- a Mission Control surface that is legible enough for real operator work, not just internal engineering use

## Trust and Security Posture

The repo may make these claims at `1.0`:

- The Gateway-owned Evolution Control Plane is the canonical authority for durable self-configuration and improvement workflows. Chat and Settings project the same Change Plan records and adapters; `change.request` may create a bounded secret-free plan but cannot confirm or apply it. See [docs/EVOLUTION_CONTROL_PLANE.md](./EVOLUTION_CONTROL_PLANE.md).
- Provider credentials, OAuth material, and native source paths use dedicated owner flows and are excluded from generic Change Plan responses, Chat transcripts, model context, and public plan projections. A provider credential is staged under a plan-bound temporary owner and is promoted only after exact confirmation.
- Model-driven filesystem tools write only inside the runtime write jail and operator write roots. Operator write roots are separate folders the operator opens through Settings or a confirmed `operator_write_root` Change Plan; each is validated against the write-root safety rules, and deleting inside one needs its own `allowDelete`. The policy engine and the tool executor both enforce the central write gate. Deny-wins, approvals, Citadel Wards and hard-forbidden runtime paths (config, secrets, SQLite and Postgres databases, audit) still apply inside every root. Chat approvals and path values in prompts do not widen write scope. See [Filesystem Write Authority](./FILESYSTEM_WRITE_AUTHORITY.md).
- Generated skills and source patches are proposals, not mutation authority. Capability candidates remain non-callable until governed activation; source patches remain isolated artifacts until a separate approved helper apply. Packaged installs reject generated patches and remain inside the verified signed-installer boundary.
- Code Mode is a governed trusted-code capability launched from Chat with explicit operator approval and bounded artifacts. The assistant can request a run itself with `code_mode.request`; it still needs that explicit operator approval, and the approved code's hash is checked at execution.
- Code Mode may stage self-authored `SKILL.md` candidates from capability-gap proposals, but staged candidates are inspectable-only until governed activation verifies artifact hashes and records approval evidence.
- Code Mode host isolation is best-effort and fail-closed when required isolation is unavailable.
- `no_agent` cron jobs run a local command (no model call, `shell: false`) under the operator-only `/api/v1/cron` route class; proof lane `pnpm verify:cron:no-agent`. A job runs an operator-specified executable with the Gateway's privileges and inherited environment; there is no command allowlist or workdir jail and no per-run approval. Every run has a timeout (default 5 minutes, capped at 60 minutes) and always settles: on timeout the Gateway kills the process tree (Windows `taskkill /T /F`; elsewhere the child runs as its own process group and the group is sent SIGKILL), and a run whose stdio is still held open by a descendant settles at most 2 seconds after the timeout or after the direct child exits. The tree kill is best-effort: a descendant that leaves the tree or process group (for example by starting its own session or process group, or on Windows a descendant whose parent already exited) can outlive the run. Captured stdout/stderr are bounded (about 1M characters each, tail kept), and stored or broadcast stdout is redacted and bounded (16K characters). `lastRunOutput` is written on every run, including failed runs, and is committed before the `cron_no_agent_output` realtime event; a rejected realtime publish does not change the run outcome. Upgrade note: the one-time `pause_dormant_no_agent_cron_jobs` migration (SQLite v267, Postgres v215) disables enabled `no_agent` jobs that never ran under the old gate, so an operator re-enables each one through the cron API after reviewing its command; `cron-jobs.json` cannot switch such a paused, never-run job back on. Jobs that already ran keep their state. Each run records an `ok` or `failed` outcome (failed runs carry the exit code, a timeout flag, and a bounded, redacted stderr summary) and evidence like system cron runs. The former `GOATCITADEL_EXPERIMENTAL_NO_AGENT_CRON` gate is removed.
- A cron job may carry a `citadelId` (set on create/update through the cron API; the citadel must exist and be active, and `null` returns the job to global scope). Every run of a citadel-scoped job, due, manual or forced, re-checks the citadel and is refused when it is archived or gone instead of running as a global job. An `agent_turn` job in a citadel with a default workspace runs in its own scheduler session in that workspace, and a configured session outside that workspace is refused. `GET /api/v1/cron/jobs?citadelId=` lists that citadel's jobs plus global jobs for the operator access class only.
- Code Mode execution backend truth is inspectable. The trusted-code host runner is the default backend; Docker is selectable only when an operator explicitly enables `codeModeDockerBackend` with an image and remains governed by the same Code Mode approval and artifact evidence path. Aider can be explicitly selected only when Docker plus `codeModeAiderAdapter` are enabled with images; it runs in run-temp/artifact space as an audit-only adapter and records request, invocation-plan, stdout/stderr, result-envelope, and optional patch evidence. Aider runs stay audit-only. Runs created against a ready, clean Chat workbench are pinned to its HEAD and seeded from that commit in an isolated baseline (the operator repo is never mounted and no content is written to it). A `patch_produced` pinned run can be promoted via `POST /api/v1/code-mode/runs/:runId/promote` under a separate `code_mode.aider_promote` approval that re-checks the patch sha256 and the pinned HEAD and tree state and applies through the workbench (`git apply --check`, then apply) at most once (an interrupted promotion is never re-applied and is left for manual review); unpinned runs cannot be promoted. A finished pinned run can be replayed through `POST /api/v1/code-mode/runs/:runId/replay` as a new run that reuses the recorded request, input and source at the same pinned HEAD/state behind its own `code_mode.run` approval (refused when the workbench moved; its patch reaches the workspace only through the same promote path, and the original run and any promoted patch are never re-applied). Candidate promotion remains unshipped; the Docker backend is callable once configured with a digest-pinned image and is proven in CI by `pnpm verify:code-mode:docker`; no hostile-code sandbox is claimed.
- Durable execution owns the shipped mission-session Chat resumable flow set documented in [docs/CANONICAL_RUNTIME_STATE_MODEL.md](./CANONICAL_RUNTIME_STATE_MODEL.md), including planning, research, delegation, approvals, and code-capability turns. External writeback operator actions record durable evidence envelopes; local bridge write actions, Activepieces webhook triggers, Trello card creation, Notion page create and block append, GitHub issue create and comment, and Gmail send actions now claim idempotency before crossing the external boundary and record replay outcome, replay-attempt, manual retry posture evidence, and runner-populated storage-ledger run states. Notion and GitHub writes claim idempotency but are not on the replay allowlist (Activepieces `trigger_webhook`, Gmail send, Trello card create and the local-bridge writes), so the worker neither resends nor reconciles them and an unknown outcome stays in manual review; their marker probes exist for a future reconcile-only path (Notion page create has no probe). Approved `communications.mail.send` and `communications.calendar.create` approvals execute once through approval effects; Gmail, SMTP and calendar sends claim idempotency on `comms_gmail_send`, `comms_smtp_send` and `comms_calendar_create` keyed `communications:<approvalId>`. A Citadel Ward `require_approval` effect on an integration operator action, an outbound A2A send or an A2A push delivery opens an operator approval that binds the exact request by its hash; integration and outbound requests (which can carry secrets) are stored in the approval only as an AES-256-GCM envelope under the external side-effect replay key, bound to the approval kind and hash, and when the request cannot be sealed no approval opens and the action stays blocked (a push request holds only task, peer, event and URL-hash identifiers and stays plaintext); on approve, an approval effect opens the envelope (one that no longer opens executes nothing), re-verifies the hash, re-checks the live ward (deny still wins; an integration connection or push task whose citadel or workspace changed after approval is refused) and executes the action once (integration actions and outbound A2A sends under the original request's idempotency key when it carried one, so a retried request that opened a second approval still executes once, and otherwise under `citadel-ward:<approvalId>`; a push delivery under its own per-event push idempotency key), and a rejected or expired approval executes nothing (a deferred push is recorded as blocked so later events resume; so is an approved push that could not be delivered). The approval preview carries a bounded, redacted summary of the gated request for review; execution never reads it. A mail send whose delivery outcome is unknown leaves its draft `outcome_unknown`, which is never resent or promoted to sent automatically. A draft whose send request was interrupted after it was fenced but before its approval was recorded stays fenced until an operator releases it: after a grace period the release re-links a persisted send approval that names the draft or, only when none exists, returns the draft to `draft`, and both outcomes are audited. An SMTP send probes the host's guard-vetted addresses before the mutation boundary and moves to the next address only when a probe cannot connect; once the message is being sent there is no fallback. The chat/agent comms Gmail send tool call now separately claims idempotency on its own boundary `comms_gmail_send`, wrapping the policy-engine-governed tool call, alongside the already-ledgered integration-action Gmail send path. Activepieces workflow recipe export is read-only planning evidence for operator import; it does not create flows, trigger webhooks, poll Activepieces, or make post-boundary outcomes resumable. Mission Control may enqueue a replay-audit durable run from the external side-effect ledger to inspect pre-boundary eligibility and link to Run Detail, completed Activepieces ledger rows can show returned workflow id/status/url evidence as webhook-response-only status, and an explicit Activepieces `check_run_status` read action can fetch sanitized run status through operator-configured API credentials. The replay-safe worker and durable `external_side_effect.replay` workflow may retry only failed-before-boundary or stale claimed-not-sent runs when an allowlisted owning integration reconstructs the original safe payload; generic webhook, send/retry/edit/stream replay and post-boundary unknown outcomes remain non-resumable. Production now registers an allowlisted Activepieces `trigger_webhook` replay job for that workflow, gated by kill switch `externalSideEffectReplayJobsV1Disabled` (on by default): it re-derives the safe payload from live connection config (`defaultFlowId`, empty payload) rather than any persisted request data and refuses replay on payload-hash drift as `payload_mismatch`, so only config-default Activepieces triggers are reconstructable and custom-payload Activepieces triggers have no replay job. Gmail send (`automation.gmail` `write`), Trello card create (`productivity.trello` `write`) and local-bridge writes (`write` on `productivity.apple-notes`, `productivity.apple-reminders`, `productivity.things3`, `productivity.bear`) are also allowlisted: the live path seals an encrypted replay record of the runner payload (AES-256-GCM under a secret-store key, bound to the run id and payload hash) before the boundary, and replay rebuilds the input from that record only if it authenticates and the rebuilt payload still hashes to the run with the live destination; a tampered record, a missing replay key or destination drift leaves the run without a replay job. Pre-boundary replays of Gmail and Trello probe the provider first (Gmail by a Message-ID and Trello by an idempotency marker in the card description, both derived from the run's route path, actor scope and idempotency key) and settle without resending when the effect is found. Post-boundary `unknown_external_outcome` runs are never resent: they are reconciled to `completed` only when the provider probe proves the effect landed, and otherwise stay in manual review; local-bridge runs are reconciled only when the operator attests in connection config that the bridge enforces the `Idempotency-Key` header (`idempotencyKeyEnforced`, which also permits stale-claim redispatch on live retries; the header carries a scoped digest, not the raw key), and every other post-boundary outcome remains non-resumable.
- Automatic Chat fan-out is conditional on both restoration and durable-fanout switches, explicit `auto_when_useful`, an active exact-project grant, and canonical parent/child admission. New sessions keep `ask_when_useful`; automatic children are bounded to three and cannot recursively fan out. Historical delegated runs remain inspectable.
- New `Explore workspace` delegation is temporarily unavailable while its frozen scope binding is replaced.
- `Continue in background` changes only a durable child watcher's attention projection. The child run, tool grants, policy decisions, approval/wait state, recovery, cancellation, steering, and inspection remain unchanged. `attention.state`, `attention.reason`, and any canonical blocker are projected in the background-task rail and Chat status. A blocked detached task may emit `durable.attention_required` through an already-configured notification rule, but notification absence or failure never changes durable execution state.
- Chat external-source attachment management remains available through the verified read-only import picker. New-turn selection requires explicit-context restoration and current source access; selection does not grant filesystem or network access.
- With `chatModelCouncilV1Enabled` (on by default; operators can turn it off), a new operator Chat turn may request a model council. The request is recorded in the turn's immutable feature references with a pinned primary route. Council members are advisory and tool-free; each member route is rechecked when the council resolves (provider configured or local, trusted context-window metadata, current route-config fingerprint, and the Citadel Ward `model.chat.<providerId>` decision), a refused primary fails the council closed, and every dispatch rechecks the ward again. The council resolution is bound to the admission id and reference hash, so recovery under a different binding is refused. Council requests with explicit context or from delegated child turns are rejected; routed-context council remains limited to historical profile-bound turns. The Chat composer does not offer the Council control for new turns yet; the request is API-only until the composer is gated on `chatFeatureAvailability.modelCouncil`.
- With `chatWorkspaceSnapshotV1Enabled` (on by default; operators can turn it off), a new operator Chat turn may opt into one content-free workspace snapshot. After verified workspace/project/path binding, the Gateway captures project revision, path identity hashes, capture time, and a bounded Git summary containing only head/branch and aggregate tracked/untracked/ahead/behind posture. The record is bound once into that turn's immutable feature references (keyed by the turn admission), reused on durable replay without recapture, grants no filesystem or tool authority, and is labeled point-in-time. Refresh creates a new request for a new turn; edit, retry and delegated child turns cannot request one. Missing project/repository data, unavailable Git, failed verification, or path-identity drift is recorded as `unavailable`, never inferred as healthy. Historical profile-bound snapshot records remain inspectable. The Chat composer does not offer the snapshot request for new turns yet; it is API-only until the composer is gated on `chatFeatureAvailability.workspaceSnapshot`.
- With explicit-context restoration disabled, new Chat turns reject nonempty `contextRefs` before source reads. Enabled ordinary operator turns retain v3 immutable admitted bytes and exact admission identity. Edit and retry admit refs they carry as a fresh turn-bound snapshot. With `chatExplicitContextBranchesV1Enabled` (on by default, effective only while explicit context itself is enabled), an edit or retry that sends no refs re-admits its source turn's admitted source ids on the new turn (an explicit empty list opts out), and a delegated child step inherits its parent durable turn's admitted session-independent ids (memory items, personal notes, generated artifacts) after the parent snapshot id/hash match the parent's durable payload. Session-bound attachments and external attachments stay with the parent session and are not inherited, because the child runs in its own session. Inherited ids are re-admitted under the new turn's own admission, session scope, source access, provenance and budget; admitted bytes and snapshots are never copied or reused, and a child request still cannot name refs of its own. The child path is covered by focused tests, not yet by an end-to-end delegated run.
- With `chatWorkPassportV1Enabled` (on by default; operators can turn it off), a new operator Chat turn classifies one Work Passport at admission, records it in the turn's immutable feature references, reuses that record on durable replay, and renders it as an advisory system instruction. It is not an occupation or competence assessment, grants no tool or capability, and does not replace policy, approvals, or accountable review. Historical profile-bound passports remain inspectable. See [docs/WORK_PASSPORT.md](./WORK_PASSPORT.md).
- When `chatSessionStatusV1Enabled` is enabled, `GET /api/v1/chat/sessions/:sessionId/status` is the operator status owner and the existing `session.status` tool receives a smaller model-safe projection from the same `ChatSessionStatusService`. `/status` is intercepted in Chat and never creates a model turn. Sections whose canonical evidence cannot be resolved are `unavailable`; the UI must not translate missing build identity, usage, context, capability, worker, or recovery evidence into zero or healthy values.
- Routed-context admission and replay recheck source access without replacing admitted bytes. Unsupported provider capacity fails closed instead of dropping context.
- `context.list`, `context.grep`, `context.query`, and `context.read_range` require their existing tool switch and a valid bound snapshot; historical profiles and restored admission-bound snapshots remain distinct variants.
- Existing routed-context v1/v2 snapshots retain their bytes and hashes. The document drawer exposes inclusion only when the server reports explicit-context availability.
- When `notificationRoutingV1Enabled` is enabled, Settings exposes revisioned workspace notification targets/rules, test delivery, and delivery evidence. External destinations are either existing configured channel connections or allowlisted HTTPS webhook URLs and optional credentials resolved from OS-keychain references at the final transport boundary. Models and Chat requests cannot provide raw destinations or credentials, and `notify.request` cannot select target IDs; operator-authored rules remain the external routing authority. Focused/visible presence is a short-lived lease, so missing or expired presence is truthfully treated as away. Delivery uses idempotency, bounded retry, redaction, audit-side-effect evidence, and explicit `unknown_after_send` state rather than reporting ambiguous sends as success.
- The dormant external connector catalog may import a pinned MindStudio Connector Registry snapshot for operator review. These entries use `kind=external_connector`, `maturity=disabled`, and `runtimeAvailability=blocked`; they expose service/action metadata, configuration summaries, docs previews, handler hashes, review state, and capability-proposal staging only. Imported MSCR handlers, SDK dependencies, OAuth flows, and external side effects are not executable runtime paths until a specific connector is reimplemented or promoted through GoatCitadel capability governance, policy, diagnostics, tests, and durable side-effect evidence.
- A2A v1.0 is the governed external agent-to-agent interoperability boundary at the Gateway. Callable support includes JSON-RPC over HTTP/S, peer-authenticated HTTP+JSON task routes, peer-configured task push notification delivery, authenticated extended cards, and Gateway-owned gRPC task transport when explicitly enabled, configured with peer credentials, and covered by Gateway-owned peer auth, deny-wins policy, durable task bindings, audit, network allowlists, focused service/route tests, and `verify:a2a:full`. Public Agent Card discovery at `/.well-known/agent-card.json` remains disabled by default. Authenticated extended cards are peer-gated, not public discovery. A2A does not replace GoatCitadel mesh; mesh remains the native coordination fabric for readiness, leases, ownership, replication, failover, and LAN/WAN/tailnet runtime state.
- Approval follow-on work is surfaced through explicit approval effect records rather than inferred from scattered side tables or inline helper effects.
- Citadel Ward `route_local` is enforced for Chat model routing: route resolution evaluates `model.chat.<providerId>` against the session's workspace Citadel and keeps or switches the turn to a model whose endpoint is a loopback host (any engine; a LAN host does not count as this machine), and fails the turn closed with `citadel_ward_route_local_unavailable` when no such model is available. Every model dispatch that carries Chat content re-checks the ward against the exact request URL: turns and their tool loops, repairs and fallbacks (including durable resumes and turns that reuse a frozen route), delegation workers, assembly calls, and utility calls with a session or turn lineage. Ward-refused fallback targets are dropped, a refused session-scoped utility call either degrades the way an unavailable utility model does or fails closed with the ward policy message, and a dispatch-time refusal names its ward reason code in the turn's failure diagnostics. A `deny` ward on `model.chat.*` blocks those dispatches with `citadel_ward_deny`. Utility calls without a session or turn lineage, embedding and image-generation calls, and `model.tool.*` actions are not ward-gated yet. `route_local` trusts any loopback endpoint as this machine; a loopback proxy (for example LiteLLM) that forwards to a remote provider is not detected. Remote worker Chat placement (`chatRemotePlacementV1Enabled`, off by default) runs the turn on another node and is not ward-gated.
- `MemoryLifecycleService` is the operator-facing memory lifecycle owner for context composition, explicit recall, trace-derived memory proposals, recall-quality feedback, memory quality issue scans/queueing, learned-memory policy, and memory item list/edit/forget/history.
- Canonical Chat messages persist server-owned source authority. External-channel and unknown messages may produce only redacted, deduplicated trace candidates; they cannot create active learned memory without operator promotion. Rebuild uses canonical messages rather than authority-less transcript projections, rejection is durable, and legacy untrusted learned memory remains disabled for operator review after migration.
- Memory retrieval evidence is native hybrid ranking: BM25-style lexical scoring, optional semantic-hint scoring from operator-visible memory item metadata, optional caller-supplied embedding similarity when embeddings are present, recency, and source diversity. `1.0` must not describe this as hidden autonomous memory promotion, Memori integration, or external embedding search beyond the recorded retrieval strategy.
- QMD assembly is budgeted before distillation: ranked candidates are selected against an evidence-token budget, the full available pool remains visible through assembly quality metadata, and selected-budget truth is persisted in the existing memory-context quality JSON without a hidden store or schema migration.
- Memory context placement is explicit and subordinate. Retrieved memory context is inserted after leading system/policy messages and immediately before the final user message when present, with manifest metadata recording the placement; it is supporting context, not higher-priority instruction.
- Library Memory may present existing records with the explanatory taxonomy `working`, `episodic`, `semantic`, and `procedural`. Those labels do not create a new permission model, authority class, graph/vector store, or autonomous promotion path.
- Trace-derived memory must remain proposed by default. Promotion into trusted memory requires operator authority or the existing write-gate path, browser-content guard evidence remains mandatory, and raw tool outputs, logs, browser content canaries, and secret-like payloads are not durable memory.
- Chat recall flows are explicit API/UI flows: targeted recall, broad summary recall, and post-compaction resume context. They may return inspectable context packs, feedback records, and open memory quality issues, but they must not be represented as invisible automatic prompt injection.
- Skill imports validate a portable `goatcitadel.skill-bundle.json` manifest with per-asset hashes and review-only script disposition. Every exact model-facing `.md` and `.txt` source is also subject to the current versioned whole-source promptware scanner. Detected, incompletely scanned, malformed-UTF-8, or stale-policy skill content cannot be installed, staged, activated, or waived through high-risk confirmation/approval. Activated bundled and external skills are rescanned after hash/receipt verification and again as the rendered instruction bundle; a finding fails the Chat turn as `skill_security_blocked` before provider execution and exposes only hash-based review evidence. Workspace `PRODUCT.md` / `DESIGN.md` documents injected by a design-skill route are scanned the same way and fail the turn as `guidance_security_blocked` with recovery action `review_workspace_guidance`, naming the file but never its content.
- Provider secrets may persist in local env or config files when secure-store persistence is unavailable or disabled.

The repo must not claim these at `1.0` unless separately proven and documented:

- cross-platform public hostile-code sandboxing for Code Mode unless `hostileSandboxClaim.publicClaimAllowed` is true and `verify:code-mode:hostile-sandbox` has green native Windows, macOS, and Linux proof; Windows-only wording may mention `hostileSandboxClaim.platformClaims.win32.publicClaimAllowed` only when the Windows AppContainer canary proof is green on the exact release SHA
- Docker or Aider Code Mode execution parity beyond the documented configured-Docker path and audit-only Aider adapter
- silent or ungoverned autonomous high-risk tool activation
- `packages/mesh-core` readiness unless `verify:mesh:readiness` is green for join-token lifecycle, mTLS/tailnet posture, lease lifecycle, owner failover, replication offsets, Settings visibility, and Gateway diagnostics
- A2A public discovery by default or A2A mesh readiness claims; A2A gRPC remains an external Gateway transport and does not replace mesh readiness, leases, ownership, replication, failover, or LAN/WAN/tailnet runtime state
- NPU sidecar maturity, local-inference completeness, or ONNX/NPU acceleration as a `1.0` signal; the former sidecar path is retired from the shipped source and installer until real hardware proof justifies a new implementation
- imported external connector coverage as live integration execution, managed workflow lifecycle, provider-auth readiness, or callable tool availability

## Upgrade and Backup Guarantees

`1.0` must stay explicit about compatibility and recovery:

- REST and SSE contract changes are additive unless a separately documented migration window is announced.
- Chat conversation forks are independent materialized sessions, not context links. Forking is limited to settled terminal paths, uses revision CAS when supplied, copies attachment bytes and generated artifact versions, and retains immutable source provenance without replaying or duplicating execution evidence.
- Chat timers are durable, provider-free reminders owned by the Gateway. `/timer` opens an explicit confirmation form, and firing appends a retained `timer_due` system notice plus one canonical notification event without invoking a model. Explicit cancellation uses revision CAS; optional reply cancellation occurs only after a new user message commits. Timers are bounded to a five-second minimum, one-year horizon, 25 active timers per Chat session, and 100 per workspace. `/schedule` remains the distinct model-running scheduled-turn path.
- Persistent configuration evolution flows through the Gateway-owned Change Plan adapters. The managed GoatCitadel config-sync path remains a low-level owner where applicable; it is not a second mutation authority.
- Storage migrations are forward-upgrade paths. Rollback across schema changes is not promised; restore from a verified backup is the supported recovery path.
- Backup create, list, and verify are shipped through the admin API/CLI surface.
- For filesystem-backed `1.0` runtimes, restore is offline CLI-only through the shared offline restore entrypoint; operators must stop any gateway serving the same runtime root before invoking it, and the live admin restore route remains additive-compatible by returning `offline_restore_required` with an offline restore hint instead of mutating the active runtime.
- Backup verify must report both archive integrity (`verified`) and minimum-set contract truth (`contractVerified`) for current `1.0` backups.
- Minimum operator backup set remains:
  - `data/index.db`
  - `data/transcripts/*.jsonl`
  - `data/audit/*.jsonl`
  - `config/*.json`
- Postgres backups are part of the shipped create/verify surface, but restore remains an operator-run `pg_restore` workflow rather than the SQLite file-copy restore path.
- Replay/import rebuild from logs is not part of the shipped `1.0` backup guarantee unless separately documented here.

## Ecosystem Contract

Before `1.0`, any visible provider, channel, MCP transport, or extension/SDK path must either:

- pass the same operator-ready parity bar as the rest of the product, or
- be removed from the visible `1.0` surface and public claims

That means:

- no visible provider may skip runtime connectivity, model discovery, readable auth/proxy/TLS errors, or usage reporting expectations without being called out here
- no visible built-in channel may remain `planned` or parity-incomplete
- no visible `beta` or `native` non-channel integration may advertise read/write/search/capture capabilities without matching operator actions in the shipped runtime
- visible `external_connector` entries are an explicit exception to live integration parity only because they are disabled, blocked, catalog-only, and non-callable by contract
- no visible MCP transport may remain unsupported for runtime invocation or omit auth readiness when OAuth is required
- the public extension author story must stay aligned to the `@goatcitadel/extensions-sdk` package contract: `1.0.0` is the last published version, and the workspace's `2.0.0` keeps the effective-tool snapshot helpers and adds the plugin manifest validator (`parsePluginManifest` and `loadPluginManifest`) and the `goatcitadel-plugin-preflight` command
- Plugins, bundles of skills, connectors, tool-group holds, observe-only hooks and prompt packs that run no code, can be inspected, installed and uninstalled only through the Gateway's Capabilities API (`/api/v1/capabilities/plugins`), and each install and uninstall is governed by a Change Plan (see [docs/EVOLUTION_CONTROL_PLANE.md](./EVOLUTION_CONTROL_PLANE.md)). Mission Control has no Plugins tab yet, and there is no plugin trust or marketplace surface.
- Arena, the add-on machinery and integration plugins were removed; the plugins above replace them. Settings › Advanced keeps capability packs as an experimental local/operator-reviewed surface in `1.0`, not a public marketplace claim. Capability packs may be previewed, staged as durable review evidence, listed, and exported as read-only manifests; graduation still requires real asset activation, permission grants, durable operator logs, rollback/version proof, runtime health, and explicit local-vs-marketplace boundaries.
- Desktop/mobile continuity claims must remain anchored in gateway auth, signed device grants, desktop daemon/runtime state, and gateway-owned sessions/projects/artifacts/approvals. The product may show mobile companion readiness, but it must not imply an ungoverned mobile control plane.
- MCP server-mode may be described as a limited `goatcitadel mcp-server` stdio proxy plus operator-authenticated Gateway routes for read-only, closed-world callable descriptors. Remote MCP invocation over Streamable HTTP (`http`) or the legacy HTTP+SSE handshake (`sse`, which only POSTs to a same-origin, allowlisted message endpoint announced on the event stream) is a separate governed Gateway bridge (requester-scoped records use Streamable HTTP only; a requester-scoped `sse` record is not callable) for no-auth servers, token-auth servers with explicit env-key policy, or OAuth2 servers with configured OAuth metadata and ready OS-secret token refs in `mcp_auth_state_v1`. Missing, expired, or unrefreshable OAuth tokens must be reported as `needs_auth`, and none of these paths prove a standalone Gateway-free MCP server.
